## 1. 프로젝트 목표

### 우선순위

1. 실제 사용자가 반복해서 사용하는 앱 만들기
2. 수익 가능성 탐색
3. 포트폴리오로 보여줄 수 있는 완성도 확보

### 첫 출시 범위

#### 확정

- 앱인토스 미니앱 1개를 먼저 출시한다.
- 2026년 7월 31일까지 앱인토스 검수 요청을 제출한다.
- 결제가 있어야 성립하는 서비스는 첫 제품 후보에서 제외한다.

#### 후순위

- 독립 iOS 앱
- 독립 Android 앱
- 별도 웹 서비스
- 결제 연동

독립 앱과 별도 웹 서비스는 반복 사용 가능성을 확인한 뒤 검토한다.

## 3. 기술 스택 기본안

제품이 정해지기 전에는 아래를 기본값으로 둔다. 제품 요구사항이 생기면 변경한다.

| 항목 | 기본 추천안 | 변경 조건 |
|---|---|---|
| 첫 출시 형태 | 앱인토스 미니앱 | 확정 |
| 클라이언트 | WebView SDK 2.x + React + TypeScript | 네이티브 수준 성능이 필요하면 React Native 검토 |
| 디자인 시스템 | 앱인토스 TDS | 비게임 미니앱은 필수 |
| Swift | 사용하지 않음 | 독립 iOS 앱 출시 단계에서 검토 |
| 저장소 | GitHub 단일 저장소 | 규모가 커지면 분리 검토 |
| 디렉터리 | `miniapp/`, 필요 시 `api/`, `docs/` | 제품 선정 후 조정 |
| 백엔드 | 필요한 경우 단일 API 서버 | 팀이 가장 익숙한 언어로 결정 |
| DB | 필요한 경우 PostgreSQL 우선 검토 | 제품 데이터 구조에 따라 결정 |
| 로그인 | 필요한 경우 토스 로그인 우선 검토 | 자체 계정이 반드시 필요할 때만 별도 설계 |

### 백엔드 판단 기준

다음 중 하나라도 필요하면 백엔드를 둔다.

- 사용자별 데이터를 여러 기기에서 저장해야 한다.
- AI API 등 외부 API의 비밀키를 숨겨야 한다.
- 로그인 검증 또는 권한 처리가 필요하다.
- 민감한 비즈니스 로직이 있다.
- 서버에서 집계하거나 추천할 데이터가 있다.

단순 로컬 도구형 미니앱이면 백엔드 없이 시작할 수 있다.

### 백엔드 프레임워크

제품 선정 후 팀 역량을 보고 결정한다.

| 후보 | 장점 | 선택 조건 |
|---|---|---|
| Spring Boot + JPA | 구조화된 서버 개발, Java 경험 활용 | 팀 내 Spring 경험자가 있을 때 |
| Python + FastAPI + SQLAlchemy | 빠른 구현, AI 연동 편의 | Python 경험과 AI API 연동 비중이 높을 때 |

첫 MVP에서는 백엔드를 여러 서비스로 나누지 않는다.

## 4. DB 및 ERD

### 기본 원칙

- 제품이 정해지기 전에는 테이블을 확정하지 않는다.

- ERD는 핵심 사용자 흐름을 정한 뒤 작성한다.

## 5. 로그인

### 원래 검토했던 기능

- ID
- PW
- Email 인증
- 닉네임 중복 확인
- 비밀번호 찾기
- 생체 로그인

### MVP 판단 기준

위 기능은 모든 앱에 공통으로 필요한 것이 아니다.

| 상황 | 추천 |
|---|---|
| 개인화 저장이 필요하지 않음 | 로그인 없이 시작 |
| 사용자별 데이터 저장이 필요함 | 토스 로그인 우선 검토 |
| 자체 회원 체계가 반드시 필요함 | ID·PW, 이메일 인증, 닉네임 정책 별도 설계 |
| 독립 앱을 출시함 | 생체 로그인 필요성 검토 |

앱인토스 토스 로그인은 계약과 콘솔 설정이 필요하다. 필요 여부를 제품 선정 직후 판단한다.

## 9. 앱인토스 출시 준비

### 공식 문서 기준 주의사항

- 앱인토스 SDK 2.x를 사용한다.
- 2026년 3월 23일 이후 SDK 1.x로 빌드한 번들은 업로드할 수 없다.
- 비게임 미니앱은 TDS를 사용한다.
- 비게임 미니앱은 앱 내 기능을 최소 1개 이상 등록한다.
- 앱 번들은 압축 해제 기준 100MB 이하여야 한다.
- 검수 요청 전 샌드박스 테스트를 진행한다.
- 검수 요청 전 토스앱 QR 테스트를 최소 1회 완료한다.
- 검수 요청 후 검토는 영업일 기준 최대 3일이 걸릴 수 있다.
